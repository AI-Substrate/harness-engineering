Harness Telemetry · field reference

counts-only · OTLP/OTEL · one ref per session

The committed telemetry files, field by field.

Every harness session publishes its telemetry as a small, self-contained tree on an out-of-tree git ref — never on main, never in your working tree. Two JSONL files carry the whole story: one holds the raw event stream, the other the derived measures. This page documents what lives in each, and what every field means.

01

The published tree

The capture preamble runs before every harness <verb>, reads everything that happened since the last command, and writes a counts-only segment to a gitignored buffer. A separate explicit step — harness telemetry sync — rolls a session's buffered segments up into a single orphan commit and force-pushes it to one ref, keyed at the session's start date. The tree it writes is flat and always complete:

# refs/harness-telemetry/<start-YYYY>/<MM>/<DD>/<session> — orphan commit, rewritten every sync session.logs.jsonl OTLP Logs — the event stream, one logRecord per event session.metrics.jsonl OTLP Metrics — the derived rollup, one datapoint per measure manifest.json — { format, session, start_date, max_seq } <seq>.json — loose fallback, only for a seq with no OTLP pair
Logs signal
session.logs.jsonl

The source of truth. Each line is one OTLP LogRecord for a captured event — a prompt, a batch of tool calls, a turn boundary, a harness verb. The rollup is recomputed from this, so it round-trips exactly.

Metrics signal
session.metrics.jsonl

The measures, derived. Cumulative-per-session datapoints for time, tool calls, skill runs and token usage — never zero-filled, never stitched across sessions.

Index
manifest.json

A four-field header a reader peels first: the rollup format, the session id, the start date the ref is keyed on, and the highest segment sequence.

02

The shared envelope

Both files wrap their records in the same OTLP structure (resourceLogs → scopeLogs → logRecords and resourceMetrics → scopeMetrics → metrics → dataPoints). The Resource and Scope attributes below appear once per record in both files — they identify the session and pin the schema so a collector ingests it untranslated.

FieldLayerWhat it carries
service.nameresourceAlways harness — the producing service.
service.versionresourceThe harness CLI version that emitted the segment (e.g. 0.10.0).
harness.session_idresourceThe session UUID — matches the ref name and the manifest.
harness.harnessresourceThe detected agent harness: claude-code, copilot-cli, … (Cursor later).
harness.commandresourceThe top-level harness verb whose preamble captured this segment.
harness.branchresourceThe git branch checked out at capture time.
harness.schema_versionresourceSegment schema version — kept in lockstep with the Scope version.
harness.envresourceA closed key-set of ambient context — e.g. PIJ_HARNESS, PIJ_PARENT_ID, PIJ_SESSION_ID. Fixed vocabulary, not free-form.
schema_urlresource + scopePinned …/schemas/telemetry/v0.1.0 — freezes naming against OTEL semconv churn.
scope.name / versionscopeharness.telemetry + the schema version (e.g. 2.2).

Naming rule: reconstruction-critical data is owned under harness.*; only stable OTEL GenAI names (gen_ai.usage.*, gen_ai.request.model) are adopted for interop.

03

session.logs.jsonl — the event stream

Every LogRecord carries three attributes that identify it before anything type-specific: harness.event.kind (its exact kind — OTLP's LogRecord has no native event name), harness.event.t (the verbatim ISO timestamp, because timeUnixNano loses precision), and harness.event.t_precision (anchored vs estimated). Beyond those three, the attributes depend on the event kind:

prompt

A human turn of input.

  • harness.prompt.wordsWord count of the prompt.
tools

A batch of tool calls of one kind.

  • harness.tool.nameTool family — bash, view, skill, create…
  • harness.tool.countHow many calls in the batch.
  • harness.tool.span_sWall seconds the batch spanned.
  • harness.tool.signatureCoarse shape of the call, e.g. pij, grep, cd.
  • harness.tool.result_tokensEstimated tokens returned to context.
turn

An assistant turn boundary.

  • harness.turn.dur_sDuration of the turn in seconds.
harness

A harness sub-verb ran.

  • harness.verbThe sub-verb, e.g. flow nav, flow create, flow render.
  • harness.observe.kindPresent ONLY when verb === observe (plan 056): the observation kind, a closed 8-value enum (difficulty · magic-wand · gift · insight · coordination · improvement-suggestion · confusion · win). A fixed-vocabulary token, never prose — it lets the offline conversion query split friction capture by kind.
command

A top-level command resolved.

  • harness.command.verbThe command name.
  • harness.command.exitProcess exit code.
  • harness.command.statusOutcome classification (ok / degraded / error).
checks

A harness checks gate ran.

  • harness.checks.statusOverall pass / fail / degraded.
  • harness.checks.gatesPer-gate roll-up (closed key-set).
skill

A skill was invoked.

  • harness.skill.nameSkill slug, e.g. builder, validate-v2.
  • harness.skill.statusHow it resolved.
  • harness.skill.dur_sDuration in seconds.
  • harness.skill.argThe argument surface it was called with.
subagent

A subagent / peer ran.

  • harness.subagent.nameAgent type or peer name.
  • harness.subagent.statusCompletion status.
  • harness.subagent.dur_sDuration in seconds.
flow

A flow-stage transition.

  • harness.flow.nameThe flow / plan name.
  • harness.flow.stageStage entered (plan, implement, review…).
  • harness.flow.statusStage status.
  • harness.flow.fromPrior stage it moved from.
flow_log

A flight-plan mutation (node/edge op).

  • harness.flow_log.opThe operation performed.
  • harness.flow_log.nodeNode touched.
  • harness.flow_log.from / toEdge endpoints for a move.
  • harness.flow_log.type / edge_opNode/edge kind & edge operation.
branch

A git branch changed.

  • harness.branch.from / toOld and new branch names.
artifact

A plan artifact was written.

  • harness.artifact.type / pathArtifact kind & its path. The closed type set gains retro (plan 056) alongside review / plan / workshop / dossier / tasks / execution-log / backpressure / validation / ship-report / flight-plan.
  • harness.artifact.plan_idOwning plan.
  • harness.artifact.changecreated / modified / deleted.
  • harness.artifact.counts / enumsStructured counts & enum tallies. A retro artifact adds (plan 056): observations (total entries); disp_* — the drain-outcome mix, one key per disposition (disp_fixed_now · disp_task · disp_plan · disp_diffs · disp_command · disp_kept · disp_declined · disp_deferred); and kind_* — the observation-kind mix (kind_difficulty · kind_magic_wand · kind_gift · kind_insight · kind_coordination · kind_improvement_suggestion · kind_confusion · kind_win). Counts-only — fingerprints and description prose never travel.
  • harness.artifact.size_lines / size_bytesArtifact size.
api_error

A model/API error surfaced.

  • harness.api_error.signatureCoarse error signature (no payloads).
usage / model

Token & model interop (stable OTEL names).

  • gen_ai.request.modelModel id for the turn.
  • gen_ai.usage.input_tokens / output_tokensPrompt & completion tokens.
  • harness.usage.cache_read / cache_createPrompt-cache token counts.
  • harness.effortReasoning-effort setting where reported.
04

session.metrics.jsonl — the measures

The rollup is recomputed from the log stream, never authored separately — so it can never drift from the events. Temporality is cumulative, per session: each CLI run is a fresh metric lifetime. An empty stream produces no datapoints rather than zeros. Split dimensions (the by column) ride as datapoint attributes.

MetricUnitSplit byMeaning
harness.session.wall_secondss—Total elapsed wall time for the session window.
harness.session.agent_working_secondss—Time the agent was actively working.
harness.session.human_secondss—Time attributed to the human.
harness.session.idle_secondss—Idle time inside the window.
harness.session.working_ratio1 · gauge—agent_working ÷ wall — how busy the session was.
harness.tool.calls{call}tool.nameTool-call counts, one datapoint per tool family.
harness.skill.runs{run}skill.name, statusSkill invocations by slug and outcome.
harness.flow.stage_secondssflow.stageTime spent per flow stage.
harness.command.exit_code—command.verb, statusCommand exit codes, by verb and status.
gen_ai.client.token.usage{token}gen_ai.token.typeToken usage split by type (input / output / cache).

06

In practice — what the data answers

These fields aren't collected for their own sake. The downstream eng-thrive program and the flow-conformance evals read the committed refs and engineer measures from them. The five examples below are real — drawn from the md → PDF conformance eval (one task, four doctrines, five models, 18 runs) and the artifact-semantics sweep over this repo's plans.

Where does a build actually spend its time?
event: flow flow.stage_seconds flow.stage

Flow-stage transitions in the log stream bracket each stage; the metric bins the time between them. Run the same task under a mandated flow and the shape of the work falls out — per model, in minutes, straight from the CLI's flow-nav events.

GPT-5.5 17.7m
Sonnet 5 33.8m
Opus 4.8 29.6m
GLM 5.2 21.0m
research plan implement review ship
Implement dominates, ship is a rounding error. Opus 4.8 poured 12.0 of its 29.6 minutes into implement; GPT-5.5 split evenly between implement and review (6.7 / 6.3). None of it was self-reported — it's the gap between consecutive flow events. md → PDF, flow-mandated batch · refs/harness-telemetry/2026/07/03/*
What does mandating a methodology cost?
gen_ai.usage.input_tokens tool.result_tokens tool.calls

Every tool batch and token bucket is counted, so the price of a doctrine is just a sum. On the identical task, mandating the full guided flow ran ×2.4–3.4 the credits of a blind run; a minimalist "ponytail" doctrine ran ×0.40–0.86.

Same deliverable, an ~8× spread in cost — visible only because the sensor counts token usage and tool calls on every command, so process overhead is measurable rather than anecdotal. md → PDF rollup · 4 doctrines · 18 runs
Did the engineering loop actually run — or just get claimed?
event: harness harness.verb skill.name checks.status

A harness event only exists if the harness verb actually fired. That makes the stream a conduct record, not a self-assessment: in the ponytail batch the engineering loop ran in 0 of 4 sessions (no harness verbs present); with an explicit carve-out it was restored in 3 of 3.

You can't fake an event you never emitted. Whether a process was followed is answered by presence in the log stream, not by asking the model. md → PDF, ponytail vs ponytail+harness batches
How busy was the session — and when is "0" honest?
session.working_ratio agent_working_seconds wall_seconds

working_ratio separates active work from calendar span — the "gait" of a session. The same measures also make the sensor honest about its own blind spots: a cohort reading 0s active over 1815s wall is flagged unmeasurable (pre-instrumentation sessions), a state the attribution block distinguishes in-band from a true zero.

Estimate-honest by construction. An unavailable marker class reads as UNMEASURABLE, never as 0 — so a missing signal never masquerades as a measured one. md → PDF, batch-1 insights (active-vs-wall ratio)
Is a plan's quality actually converging across revisions?
artifact.counts artifact.enums artifact.change

The artifact extractors turn a written review into structured counts and enums. Run over the two versions of one plan's review, the trajectory reads itself: v1 — 2 high + 1 medium finding, verdict FIX_REQUIRED; v2 — 0 findings across 4 re-reviews, verdict APPROVE.

Convergence, straight from the counts. No human summary in the loop — findings-down / verdict-flipped is a measure, drawn from artifact.counts + artifact.enums. artifact-semantics sweep · plan 050 review v1 → v2
07

Guarantees & policy

↺

The reconstruction invariant. The OTLP Logs round-trip to the exact event stream, and the rollup is recomputed for free (rollup = computeRollup(event_stream)). It's proven by a deep-equal round-trip over the real sampled-session corpus, drift-checked in CI by npm run check:telemetry-fixtures.

◇

Counts-only, estimate-honest. Every number is either an exact count (events, tool calls, commands) or a declared estimate (time and token attribution). The sensor emits and commits faithful counts — it builds no scanner, no dashboard, no correlation. The read path issues only for-each-ref + cat-file; it never reads git config user.email.

⌦

Never in your working tree. The buffer and the OTLP spool live under a self-ignored .harness/temp/; sync publishes over git plumbing to an orphan ref, never touching your index. A failed push rolls the local ref back and keeps the buffer intact, so a buffered segment is never lost — and never committed to a work branch.

⚑

Frozen contract. The complete attribute vocabulary is pinned in otlp/harness-otlp.schema.json, held key-set-equal to the single mapping module otlp/semconv.ts by a freeze test — a semconv rename without a contract bump trips CI. To swap a name when it stabilises, edit semconv.ts and the frozen contract, nothing else.
