Engineering Harness · Flow-Conformance Evaluation

How we evaluate agent flows

We hand an AI agent a real software task, watch how it works through committed telemetry and the files it produces, and grade the finished session against written criteria — deterministically wherever evidence allows, with a tightly-contained LLM layer only where judgment is genuinely required. This page explains the whole process in plain terms, without watering any of it down.

The loop, end to end

Author a scenario

A committed data bundle: the task paragraph, a pinned base commit, the assertions to check, and two prompts (subject & runbook). Adding an eval costs data, not engine code.

Spawn a blind subject

A fresh agent gets its own worktree at the pinned commit and only the task + a reporting protocol — never the assertions, scoring rules, or hidden expectations.

Let it work

The subject does the task for real. Every harness command it runs is captured as counts-only telemetry; every file it writes lands in its worktree.

Score the evidence

harness flow-eval score reads the finished session — telemetry once, worktree directly — resolves every assertion to pass / fail / unknown, and writes the report + an append-only ledger line.

Judge, then feed back

Rubric-bound judged fields are filled after the run. Findings flow back into the harness — better sensors, better docs, better flow — and the loop runs again.

Two roles, strictly separated: the orchestrator drives the run (spawn, verify the model, deliver the packet, answer gate questions under a fixed policy); the evaluator never drives anything — it only reads what a finished session left behind. A run that finds non-conformance is a successful evaluation, not a tooling error.

Two ways of knowing: deterministic and judged

Deterministic — computed from evidence

Telemetry + filesystem lanes

  • Telemetry lane — did the skills run, in what order, did the seams fire, did checks pass, did a compaction happen? Read from counts-only session telemetry committed to git refs.
  • Filesystem lane — does the output exist, does its content match, does a real command exit clean when run in the subject's worktree?
  • Harness-loop conduct is deterministic too — did the agent record in-flight observations (harness observe), drain them into a retro, and leave the record as a real artifact? Scored from evidence, so reports and insights read an agent's suggested retro items directly — never from its self-report.
  • Every row resolves three-valued: pass, fail, or unknown — where unknown means the evidence channel was unavailable, never "the subject failed". Unknowns are excluded from every score denominator.
Judged — decided against a written rubric

The contained LLM layer

  • Rubric fields — genuinely subjective calls (e.g. "is this validator a real sensor or a token gesture?") answered after the run against a committed prompt + rubric, recorded with verdict, rationale, and who judged.
  • Artifact-only judge — a pinned model from a different family than the subject, temperature 0, identity-stripped, fed only verified artifacts (report rows, exports, worktree files) — never the subject's own prose or self-report, with an explicit anti-verbosity instruction.
The one hard rule: the LLM never produces a number that enters the deterministic score. Judges classify against rubrics; all arithmetic is code.

Two axes, so ritual can't hide a broken artifact

Every assertion belongs to a fixed axis, and each axis is scored independently (pass-rate, unknowns excluded):

Process

The prescribed ritual — did the agent work the way we teach? Skills, stage order, seams, checks, retro, compaction.

Can never force a FAIL verdict

Capability

The working artifact — does the thing it built actually exist, register, and run? Files, content, real commands.

Caps the verdict when a required row fails

Safety

The guardrail — forbidden states. Cap-only: it can sink a verdict but is never averaged into a score.

Caps the verdict when a required row fails

An axis with no scorable evidence renders unmeasured — never 0.00. A zero is only legal when there was real evidence and it scored zero.

⚑

The mimicry alarm. When process ≥ 0.80 and capability ≤ 0.40 — with both axes actually measured — the report raises mimicry: the "right ritual, broken artifact" signal. An agent that looks like it followed the flow but shipped something that doesn't work is the exact failure mode this system exists to catch.

PASS
Every row measured, nothing failed, nothing unknown.
PASS_WITH_NOTES
Some fails and/or unknowns, but no required row failed. Read the notes — an unknown-heavy pass means limited measurement coverage, not excellence.
FAIL
A required capability or safety row failed. Process style alone can never put a run here.

The overall score is weighted and unknown-excluded: score = Σ weight(pass) ÷ Σ weight(pass + fail).

The statistics — small-sample honesty

Runs accumulate in an append-only ledger, each stamped with a seed tuple (model, harness, base commit, a hash of the rubric, a hash of the subject packet). Model-vs-model comparison refuses to run unless every compared group shares one rubric hash and one base commit — comparing across a rubric change is a category error, so it's a hard error, not a footnote.

pass1 — the rate, with its uncertainty

pass¹ = passes / k · 95% Wilson CI

Mean pass rate per lane per model, always shown with a Wilson score interval — chosen over the normal approximation because k is tiny.

At k=1, 1.00 [0.21–1.00] — that huge interval is the message: one run proves almost nothing.

passk — observed reliability

pass^k = 1 iff all k runs passed · est p̂^k

Did it pass every time? Reported alongside the mean (never instead of it), with the smooth estimate labelled est so nobody mistakes a curve for a fact.

2-of-3 renders pass¹ 0.67, pass^k 0 — a mean can never masquerade as reliability.

McNemar — paired significance

χ² over discordant pairs, paired by trial key

Two models on the same trial (same seed tuple minus the model): count the trials where exactly one of them passed, test whether the asymmetry is real.

Omitted, and says so, when trials don't align 1:1 — an omitted test is honest; a forced one is not.

A difference earns the ✱ significance marker only when Wilson intervals fully separate or McNemar reaches significance. No asterisk means "not significant" — and gets narrated that way. Cost columns (tokens, credits, cache) are displayed but never ranked: cache economics differ per harness, and ranking them rewards the wrong thing. Unknown verdicts never enter any denominator — a blind telemetry lane renders —, not 0.00.

Stage semantics — where the economics come from

When a subject drives the delivery flow, its flight-plan navigation events bracket the session into stage windows, and a versioned semantic map projects them onto five canonical stages. Time and tokens are then attributable per stage:

Every window also records how it was labelled — real navigation events, a fallback, or honestly unlabeled (a recorded absence, never a guessed stage). The map is versioned, so adding new semantics later can never silently relabel old reports.

This is what unlocks fleet-level questions: stage cost profiles per model, "does more planning correlate with fewer total tokens?", and same-model-different-harness splits where the stages mean the same thing on both sides. All such claims stay correlational — a fleet of four supports "correlates with", never "causes" — and every number is computed by code, restated verbatim in any narration with its n and caveat.

Reading a report — six questions, in order

  1. What's n? One run per cell is a smoke signal, not a distribution — the Wilson width tells you at a glance.
  2. Same seed tuple? Check base commit + rubric hash before comparing anything across columns.
  3. Unknowns or fails? 3p/0f/7u means "we could measure 3 of 10 claims and all 3 passed" — a coverage statement, never "30%".
  4. What's the axis split? capability 1.00 · process unmeasured (couldn't see the ritual) reads completely differently from capability 1.00 · process 0.20 (saw it; it wasn't followed).
  5. Did a required row fail? That, and only that, is what forces a FAIL.
  6. What did the judge layer add? Judged verdicts carry a rationale and a "by" — quality calls layered on top, never inputs to the deterministic arithmetic.

The principles underneath

Blind subjects

The agent never sees the assertions, the scoring, or what "good" looks like — so the eval measures approach, not recall of the rubric.

Evidence over narrative

Telemetry and the worktree decide. An agent's own account of its work is never scoring input.

Honest unknowns

Where the evidence channel is blind, the system says unknown and excludes it — it never guesses, and never lets a measurement gap read as a failure.

Failure is a finding

A FAIL verdict is a successful evaluation. The loop exists to surface non-conformance and feed it back into a better harness.
