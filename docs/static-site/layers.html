First · The Problem

Sound familiar?

The agent says it's done — you take a look and wonder what it was up to the whole time. backpressure
Tests are green, everything passed… first real run, instantly broken. evidence
Did you even try to run this? backpressure
Twenty-five minutes of looping, just to boot the app and hit one endpoint. fewer tokens
How many times has your team solved the same setup problem? encode it once
Can your agent even run and interact with your project? harnessability
Problem 01

The loop closes too slowly.

It takes the agent too long to get real feedback from your codebase on the work it just did — so it guesses, loops, or asks you to eyeball the result.

Problem 02

The loop is hard to trust.

"Looks good to me" from a language model is inference, not proof. Quality needs deterministic validation the whole team can lean on.

It's you and the agent together that made these problems — with the right environment, most of them don't happen. And underneath both: every new agent session is a fresh developer onboarding into your codebase — cold. If the supported path lives in scattered docs and tribal memory, the agent has to infer it. Sometimes it infers well; sometimes it hallucinates confidence. Either way, you're paying for the inference. And when the agent stumbles, that's not just an agent failure — it's usability research on your engineering environment.

Then · The Idea

An engineering harness productises the development loop — so a human or agent can move from intent to evidence, then encode what they learn into the next run.

Your engineering environment already exists — it's just diffuse: package scripts, CI configs, AGENTS.md paragraphs, tribal setup steps, a Miro board from last quarter. An engineering harness turns that into a first-class concept: named, discoverable, runnable, and owned. The layer model below shows where it sits.

Layer 02 / Inference · The Agent Harness

Reasons. Plans. Judges architecture. Writes the code.

Where the agent works through ambiguity — and discovers friction. Semantic review, planning, spec-driven development: it all lives here.

The catch: this layer is probabilistic. It infers — brilliantly — but it can only claim the work is good, and every new session starts cold, re-discovering your repo from scratch. Claims need somewhere to be tested, and discoveries need somewhere permanent to live. That's the layer below.

Layer 03 / Deterministic · The Engineering Harness

Runnable proof. Trusted backpressure. Fewer tokens.

Not just automation — this is where repeated inference gets converted into executable team memory. The proof comes from sensors, not from the LLM saying things look good.

This is the layer you add. Most repos already have the pieces — tests, linters, scripts — scattered and tribal. The engineering harness makes the layer tangible: one named surface with a CLI front door, so proof comes from sensors, not from the model marking its own homework.

Layer 04 / Codebase

Bootable. Observable. Testable. Mockable. Stable.

Engineering fundamentals — the substrate that makes deterministic proof possible. If the harness is being stretched thin by the codebase, maybe it's time to change the codebase.

Bootable Observable Testable Mockable Stable

The dependency: the harness can only prove what the codebase lets it touch. Fakes, seams (the plug points where test doubles slot in), seed data, bootability — harnessability is a codebase feature. If the harness is being stretched thin, sometimes the right harness fix is a product-code fix.

That's the stack. Now — why naming one layer changes how the other three behave.

Why It Works · The Focal Point

One surface. The deterministic layer made tangible.

The engineering harness is the physical manifestation of the deterministic layer — a single surface for your whole engineering environment. Reducing all that diffuse information to one focal point buys you three things:

A

Discover in one place

A single point of discovery. --help instead of tribal memory — agents and new humans explore the supported path on demand, without polluting context, every cold session.

B

Prove with backpressure

One place where backpressure lives and grows. Deterministic verdicts — yes or no, evidence attached. The agent can say it's done; the harness decides whether that claim is supported.

C

Improve at the seam

When friction shows up — every stumble, every "if only there were…" magic-wand ask — there's a tangible place to go and do the work: a new command, check, fixture or sensor. Encode the fix, not the memory — and everyone on the repo, human or agent, gets it.

Nobody reads it. Nobody loads it into context. It just exists — and because it exists, it's how it works. It becomes physical.

"If it's designed well, pointing the agent at the CLI is almost enough to get started."

All of it folds down into something small enough to start tomorrow.

Recap · The Nucleus

Four parts. One compounding loop.

Strip everything else away and this is the irreducible core — the smallest thing that still counts as an engineering harness:

CLI focal point+ required agent use + Deterministic backpressureproof from sensors, not vibes + Friction captureevery stumble & magic-wand ask + Human-selected encodingthe human picks what gets encoded = Engineering Harness Nucleus

Installed in a repo, those four parts run as a session loop — the same shape every time, whoever's driving:

Boot→ Backpressure Check→ Do work · Observe→ Retro · Magic wand→ Encode→ ⟲

The step that makes the loop compound is Retro & magic wand. At the end of a session — before its context evaporates — you stop and ask two questions, of the agent and of yourself. Every stumble it hit was usability research on your engineering environment; every answer is a candidate fix to carry to the focal point and encode — the C move from above. Next session boots smarter than this one.

The magic-wand question

"If you had a magic wand, what one command, flag, output field, fixture, diagnostic, template, sensor, check, or workflow change would make the next run easier, safer, or higher quality?"

The companion question

"What did you have to infer that the harness should have proved?"

Don't just use agents to write code.
Use agents to improve the loop the agents themselves use.
