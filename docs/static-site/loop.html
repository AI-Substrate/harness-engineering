Rule Zero · The Front Door

You only ever call one thing.

Never call the children directly — the router owns the routing.

/eng-harness-flow is a stateless router. On every call it re-reads the repo's deterministic signals — harness doctor, the governance doc, plan artifacts, the observe buffer — works out where you are, and hands back exactly one next command. Mid-adoption it routes the first missing rung; once the gate holds, it dispatches into the loop by seam. Unsure where you are? Call it. It's always safe.

stateless — survives /compact routes exactly one step never gates · never blocks teaches as it routes

Every turn: a rail, a now, a next.

The router shows where you sit on the loop, flags anything you might have missed, and prints the one next command — copyable, never forced. Opting out is conversational: say so, and the loop skills stop being called.

stateless — recomputed from repo signals, every call

Phase 01 · Install / once per machine

Teach your agent the skills.

One command, and the whole family is on board.

The skills ship from the public AI-Substrate/harness-engineering repo via npx skills. Install them globally into your agent CLI — Claude Code, Copilot, Cursor, Codex — and your agent now knows the front door and everything behind it. Nothing has touched your repo yet; that's the next phase.

Skills are the playbooks.

This step installs the instructions your agent follows. The harness CLI — the runnable focal point — lands per-repo during adoption, where it wraps the commands your repo already has.

install · once per machine
npx skills@latest add AI-Substrate/harness-engineering -a claude-code -g -y
✓ eng-harness-flow · eng-harness-1-boot · eng-harness-2-backpressure
✓ eng-harness-4-retro · eng-harness-0-adopt · eng-harness-0-harnessability-assessment
✓ eng-harness-0-add-extension — 7 skills installed
# already in a harnessed repo? the CLI wraps the same thing:
harness skills install --target claude-code --global

Phase 02 · Adoption Gate / once per repo · boot LAST

The repo adopts the harness.

Five rungs, walked in order — the router routes the first missing one.

Point your agent at a repo and call the front door. No harness yet? The router stays on the adoption track: install the CLI, scout the repo, governance, an injection point into the flow you already run — and a working boot command, built last, deliberately, so the moment it works you run it and flow straight into real work. Adoption wraps what exists — build, test, run, as-is — it never replaces your toolchain.

Install eng-harness-0-adopt

Governance .harness/engineering-harness.md

The Boot / Interact / Observe contract — what boots it, what proves it, where evidence lands. Until it exists, the loop skills honestly report UNAVAILABLE.

Inject the injection map

Map where your extant dev/SDD flow calls /eng-harness-flow — recorded in governance, so usage is structural, not remembered. It survives every cold agent start.

Boot · built LAST eng-harness-0-add-extension

Author a boot verb that wraps what already exists — npm test, just test, your smoke script — then run it once. Never trust your own scaffold: verify with doctor, instructions, boot.

Phase 03 · The Work Loop / every session · forever

Deliver software — loop running.

It never "completes" — it compounds.

This is where you actually ship. Your normal dev flow — specs, plans, tasks, commits — runs in the middle; the loop wraps around it. Boot proves the system runs before you touch it, friction gets captured while you work, and the retro turns that friction into encoded improvements — so the next session boots smarter than this one.

Boot→ Backpressure Check→ Do Work · Observe→ Retro · Magic Wand→ Improve→ ⟲

Boot

eng-harness-1-boot --validate

Re-run the boot adoption built — prove the system runs before any code is written. Reports healthy / SLOW / UNHEALTHY — or UNAVAILABLE, which routes back to adoption, never errors.

post-spec · before you build

Backpressure Check

eng-harness-2-backpressure

Can this work be proven by deterministic sensors — build, type, test, lint, smoke — or just eyeballed? Names the missing sensors; may suggest a "Phase 0: establish backpressure." Advisory — never blocks.

backpressure-coverage.md
the moment friction happens

Do Work + Observe

npx --no-install harness observe "<what>" --kind <kind>

A CLI verb, not a skill. One silent call per noticing — a confusing failure, a retry, a slow command, an "if only there were…". No nagging mid-flow.

one entry in the gitignored buffer
phase / session end

Retro · Drain

eng-harness-4-retro --drain

The one user-facing retro prompt — a plain-language ask to save the session's notes (keep all · pick · skip) — then materialise the keepers into a committed record via harness record retro and clear the buffer.

committed team memory
plan complete · periodically

Retro · Harvest

eng-harness-4-retro --harvest

Read-only curation across every committed retro: what recurs, what's stale, what to encode next. Recurrence is framed as token cost — pay it down. Drain first if the buffer isn't empty.

the encode-next shortlist

Improve

The beat where the loop compounds: ship the fix as a command, sensor, fixture, or doc. .harness/history.md gains a row. Most loop runs encode nothing — and that's fine.

Where It Plugs In · The Seams

Riding shotgun with your SDD flow.

The harness loop doesn't replace your delivery pipeline — it anchors beneath it. A parent flow (an SDD pipeline like the-flow, a human, a CI agent) calls the front door at five seams and pins position with --event. One command per call; the parent calls again at the next seam.

your SDD flow spec→ plan→ tasks→ build→ review→ merge
You sit down to work --event session-start
⟶
eng-harness-1-boot --validate

Prove the environment runs before the first line of code — orientation by evidence, not memory.

The spec is ready, pre-architect --event post-spec --spec <path>
⟶
eng-harness-2-backpressure

Survey what's provable about the scoped work — the architect consumes backpressure-coverage.md.

Mid-build, friction hits no event — fire it the moment it happens
⟶
npx --no-install harness observe "…" --kind difficulty

One silent line per stumble. Agent friction is usability research on your engineering environment.

A phase or session ends --event phase-end --plan-dir <path>
⟶
eng-harness-4-retro --drain

Buffer non-empty → triage it into a committed record before the context evaporates.

The plan completes --event plan-complete
⟶
eng-harness-4-retro --harvest

Look across plans: what recurred, what to encode — and the Improve beat ships it.

No parent flow? Same seams, driven by you. The router is stateless, so /eng-harness-flow with no arguments is always a safe question — "where am I and what's next?" — answered from the repo itself, not from anyone's memory.

Recap · One Sentence

The loop, compounding.

Boot proves the system runs, Backpressure asks what's provable before you build, Observe catches friction while you work, and Retro turns that friction into encoded improvements — so the harness is the product, and every session starts smarter than the last.

You can drive every step by hand —
but you never have to route by hand.
