# Research Dossier: flow-conformance eval harness

**Generated**: 2026-06-29T03:05:00Z
**Query**: "Use flow-pair to have an orchestrator drive a blind subject agent through an entire the-flow journey on a fixed task, then grade flow-conformance deterministically from local telemetry/OTel + filesystem, config-driven, reporting to `.harness/live-testing/<slug>/`."
**Effort**: Deep (3 parallel investigations + lead scout)
**Tools**: Standard
**Evidence**: 16 current sources · 5 historical (plans 034–038, agents/*)

## Answer

1. **Every composable piece already exists** — the harness is an *integration* of flow-pair (orchestration over `pij`), the telemetry/OTel substrate (plans 034–038), the extension contract, and the existing eval-agent schemas. No new foundational infrastructure is required; the new work is glue + one query path + the config-driven scorer.
2. **The deterministic grading substrate is real and rich.** Each `pij` session's telemetry lands locally at `.harness/temp/telemetry/<session>/<seq>.{json,logs.jsonl,metrics.jsonl}`, keyed by `captured_env.PIJ_SESSION_ID`, with an `event_stream[]` that already records `kind: skill` (which skills ran, in order), `kind: checks` (+status), `kind: flow`/`flow_log`, `kind: harness` (verb invoked), and `files.written/edited`. That covers most "did it follow the flow?" assertions deterministically.
3. **The correlation key works two ways.** Telemetry → `PIJ_SESSION_ID` in `captured_env`; *and* `pij path <id> --events|--state|--dir` resolves the peer's on-disk transcript/events directly. The eval should use both — telemetry for counts-only structured proof, `pij path` as the robust session→disk handle (survives cwd/worktree surprises).
4. **The eval is inherently two-layer, exactly as the ask frames it.** Telemetry+filesystem prove *occurrence* (skill X called, file Y created, a `checks` event fired) deterministically; *quality/semantics* ("did it offer a **proper** backpressure checker", "did checkpoints get done right") cannot be read from counts — those are orchestrator-LLM-judged fields. The architecture must keep these lanes visibly separate (deterministic green/red + a thin judged layer).
5. **The fixed task forces a real product gap on the subject:** mermaid is *validated* today (`markdown-lint/lib/mermaid-runner.mjs`) but **never rendered**, and there is no PDF library in the repo — so "markdown→PDF with mermaids + validated outputs" is genuine, non-trivial work (good: it exercises backpressure design).

## Planning Handoff

- **Preserve**: the counts-only telemetry contract (never read content); the extension I/O surface (`ctx` only); flow-pair's forbidden-paths + compact-early + canary-verify disciplines; the CLI-is-sole-writer rule for any flow state.
- **Change carefully**: adding a `telemetry get/query <session>` path (F-07) — keep it read-only and out of the `sync` write path; worktree cwd handling (F-04 risk).
- **Likely files/symbols**: NEW `.harness/extensions/<eval-name>/extension.ts` (orchestrate + score + report); NEW telemetry-query read path (extension or core verb); the subject packet/eval-guide prompts (under the plan folder or `agents/`); report output convention `.harness/live-testing/<slug>/`. Read for reuse: `agents/flow-skill-eval/*`, `flow-pair` lib, `services/telemetry/{capture-service,events,cursor}.ts`.
- **Decisions still required** (for `plan`):
  1. **Where does the eval orchestrator live** — a new `flow-pair`-style skill/agent, a `.harness/extension`, or a thin script that *uses* flow-pair? (The ask leans: orchestrator = the Claude session running this, driving pij; the *deliverables* are prompts + extensions + scorer.)
  2. **Config schema** for assertions — shape of `{type: skill-called|file-created|checks-ran|flow-seam-fired, ...}` and how telemetry+filesystem each resolve a type.
  3. **Deterministic vs judged split** — which report fields are scored from telemetry/FS vs filled by the orchestrator LLM (backpressure quality, "checkpoints done right").
  4. **Subject harness/model matrix** — claude (opus) and copilot (gpt-5.5) first; how the report records the model under test.
  5. **Worktree pinning** — tagged base commit for the fixed task; recorded per run.
  6. **Scope of phase 1** — the ask says "later we will be adding more": almost certainly Simple-mode, single-phase first cut = one subject, one model, the deterministic scorer + the telemetry-query read path + report, with the judged layer thin.
