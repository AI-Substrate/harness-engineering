Deterministic
Documents

A new way to write documents that machines can verify and humans can read — where the markdown is a view, the data is the truth, and every claim is an address.

A deterministic document (“DD”) is a document whose source of truth is structured data: a .dd.json file in which every section declares its type, every element carries an id, and the human-readable .dd.md is generated beside it — never authored. Structure is validated, content is hashed, and anything — a plan, a flow node, a check — can point at any section or row and be told when it drifts.

01

The problem: coding in markdown

Markdown documents that carry operational state — acceptance criteria, checklists, evidence, proof plans — are programs written in a language with no parser. Every failure below is real, measured in this repo’s own plan corpus.

ROT 1

Structure lives in the reader’s head

A heading level, a bold label, a bullet convention. Every agent re-infers the document’s schema, every session, and different agents infer differently. Nothing detects a wrong inference — work proceeds on a misreading.

ROT 2

Checkboxes rot

- [x] handles declined cards has no id, no author, no timestamp, no reason. Measured: five shipped plans whose plan-doc checkboxes are all still [ ] — while a second copy in the tasks dossier was maintained. Two ledgers, nothing reconciles them.

ROT 3

References drift silently

Of 11 backpressure surveys, exactly one ever recorded which plan version it surveyed (a SHA basis) — and that one is now stale: the plan changed after the survey, and nothing noticed. The only document that tried to do it right was silently orphaned.

ROT 4

Nothing is addressable, so everything is copied

You cannot say “AC-3 of phase 2” in a form a tool can resolve — so the spine keeps no ACs at all, the plan keeps prose, and the tasks keep a paraphrase. In plan 056, an AC’s id was lost to a typo (**n** instead of **AC-03**): the criterion became unnameable, nothing could demand proof of it, and it shipped unverified.

The measured baseline Across 54 flight-plan files: zero carry any requirement field · one basis hash ever recorded (now stale) · phase instructions are byte-identical boilerplate (“done when the acceptance criteria are met”) across three harness versions. An agent resuming from the spine knows a label and a verb — never what it owes, or how that would be proven.
02

Anatomy: one truth, two views

A DD is a pair: the .dd.json holds the data — typed sections, ids, hashes; the .dd.md beside it is regenerated on every edit and never hand-touched. Running example throughout: a checkout-flow feature plan.

plan.dd.json — the truth{
  "dd": { "doc_type": "plan", "spec": "dd@1" },        ← self-describing
  "meta": {
    "title": "Checkout flow — guest payment",
    "edited_at": "2026-08-03T04:12:55Z",
    "content_sha256": "9c4e21b8…",                ← hash of sections only
    "contributors": [                              ← what fed the render (§6)
      { "path": "./backpressure.dd.json", "sha": "5d10ab77" }
    ]
  },
  "sections": [
    { "id": "plan-objective", "primitive": "free-text",
      "body": "Let a signed-out shopper complete checkout…" },
    { "id": "plan-phase-ac.phase-2",                ← stable address (§3)
      "primitive": "completable-table",
      "rows": [
        { "id": "ac-4b1c",                          ← born-once id (§3)
          "criterion": "Declined card returns a typed error, cart preserved",

Why the pair matters Humans and GitHub read the .md; tools and agents read the .json. Because the .md is a build artifact, a stale or hand-edited copy isn’t “reconciled” — it’s detected (render-drift is a doctor error) and regenerated. One representation, two views, zero divergence.
Write posture — decided (D1) Unlike the flow spine, a DD is a validated file format, not a mediated store: any person, agent, or tool may edit the .dd.json directly — dd validate / dd doctor / regeneration are the contract that keeps every edit honest. That is what makes DD portable beyond the harness.
03

Two id regimes: addresses vs records

Everything in a DD is addressable, but sections and rows need opposite kinds of identity. The rule that picks the regime: what should break when this thing is renamed?

SECTIONS · STABLE BY CONVENTION

Sections are addresses

A section id is derived, never invented: type + name → plan-phase-ac.phase-2. The same phase carries the same id in every plan file in the repo, forever — semantic, greppable, and predictable before the file even exists, which is how a flow node can point at a plan section that hasn’t been authored yet and have doctor report it as “dangling” rather than nothing.

Renaming changes the address — so renaming is a first-class operation: dd rename-section recomputes the id and rewrites every inbound link across the repo in one transaction (decided · D8).

ROWS · UNIQUE, BORN ONCE

Rows are records

An element id — ac-4b1c, bp-7f3a, el-0042 — is minted once at creation and never re-derived from content. Sharpen an AC’s wording from “handles declined cards” to “a declined card returns a typed error” and it is the same criterion: it keeps its state, its evidence links, and every inbound reference.

If row ids were derived from text, a clarifying edit would be a delete-plus-create — silently discarding completion state and orphaning every link. That is checkbox rot with extra steps.

One consequence worth saying twice “AC-3 of phase 2 of the checkout plan” is now a resolvable name: plan.dd.json#plan-phase-ac.phase-2/row:ac-4b1c. Because it can be named, it can be linked; because it can be linked, it never needs to be copied — and the copies were where every drift problem in §01 lived.
04

Section primitives

Doc types are many and open (plan, backpressure, execution-log, ADR…). Section primitives are few and closed — the shapes the tooling knows how to store, validate, gate on, and render. A plan-phase-ac section and a bp-evidence section are different types sharing one primitive.

PRIMITIVE

free-text

Prose in a named, addressable slot. Most of a plan stays prose — it just stops being the container that structure has to be guessed out of. Validate: present / non-empty.

PRIMITIVE

list

A flat enumeration with no state — goals, non-goals, notes. Plain strings, no ids. The rule: an element earns an id when it carries state or is a link target; wanting to link to a list item means you needed a completable section.

PRIMITIVE

completable-list

Tickable items with ids, a state, and evidence links — the acceptance-criteria shape, and the thing nav gates on. A completed item with no evidence is a validation error, not a style nit: an unevidenced tick is unexpressible in a valid document.

PRIMITIVE

completable-table

Same completion semantics, richer rows: typed columns — string · int · state · link. Link columns declare their target shape (“a backpressure doc’s evidence row”) and cardinality (“every AC must name its pressure”), so schema — not review habit — enforces the wiring.

PROPOSED

log (append-only)

Entries with born-once ids that may be added but never mutated or deleted — enforced by validate, not convention. The execution log becomes this (decided · D3): the durable trail AC rows point their discharge links into.

PROPOSED

record · include

record: typed key/value header (owner, linked flow, counts) — kills the bolded pseudo-table. include: transclude another DD’s section by address, storing a reference + hash, never a copy (§6).

Completion is a state, not a boolean (decided · D4)

A checkbox can only lie by omission. A state can tell the truth about why it isn’t done — and the survey found today’s spine doing exactly this damage: one status (assumed) doing double duty for “not yet” and “never ran, no record”.

□ unchecked — open; holds the gate ✓ checked — proven; passes ⊘ blocked — can’t proceed; holds, loudly ◈ human-skipped — waived by a human, receipted; passes but queryable forever

Simple bool columns still exist for plain facts — state is for things a workflow gates on. Exact vocabulary is an open workshop item (W2), including who may set human-skipped (human-only, receipted).

Open workshop item — W1 · render adapters for custom types Built-in types render natively. But DD is a platform: a team adding richer column types in their own doc types needs a story for how those render — registered per-type render adapters shipped by doc-type packages, with a mandatory honest fallback for unknown types (raw value + type tag; never a crash, never a silent blank). Flagged for its own workshop.
05

The AC row is a signpost, not a container

The row a plan renders and a flow node gates on stays light — id, criterion, state, a short note — plus two typed links pointing in opposite directions in time (decided · D2). The heavy material lives at the link targets, each in the document that owns it.

← PRESCRIPTIVE · pressure

backpressure.dd.json

What must be proven and how — selected before work. Row bp-7f3a: mode RUN, paved command npm test -- decline-path, tier computational, certainty strong.

Link carries a basis pin — the evidence doc’s content-sha when cited. If the prescription changes later, the citation goes visibly stale (§6).

The append-only trail that receipts taught the harness to demand — provided by the format, not by discipline.

06

Links, and the two hash ledgers

A link is a typed value, not a hyperlink: relative path + stable section id + row id, resolvable from anywhere in the repo. There are two ways to point at something, and they want opposite drift behaviour.

  └── relative path (repo-internal) ──┘   └─ stable section ─┘  └─ born-once row ─┘
A WINDOW · transclusion

Live, and it can never drift

The flow spine “shows” the plan’s AC section. There is no copy — it displays the plan’s rows through the link, live. Tick an AC in the plan and the flow sees it instantly, because there is only one list.

Freshness of the rendered view is handled mechanically: every render records a contributors manifest (path + content-sha of each input doc). A contributor changed → the render is stale → regenerate, automatically — cascade on edit, watcher for hand-edits, checks backstop. Auto-refresh is always correct here: regenerating a view cannot lie. (D9)

A CITATION · reference + basis pin

Pinned, and drift is the signal

AC-04 says “my proof is bp-7f3a.” That is a claim about what bp-7f3a said at the time — so the link records the target’s content-sha at citation: the basis pin. Someone later weakens that evidence row? The link still resolves, everything still looks fine — but the pin no longer matches.

Never auto-refreshed. The pin means “someone confirmed this pairing” — only a re-verify (fine, refresh the pin), re-point (cite better evidence), or contest (the target’s change was wrong) moves it. A tool silently updating it would be vouching for something nobody looked at.

How drift is “announced” — it isn’t Nothing pushes a notification. The pin makes drift computable, and the readers that already run at the right moments surface it: doctor (inside harness checks — CI catches it like a failing test) · orient (a criterion whose cited proof drifted shows as checked (stale) on the node, every turn) · the renderer (a visible marker beside the link in the .md). Same trust model as a checksum on a download: verified at the moment of use, which is the only moment that matters.
07

The graph, and the verbs that walk it

Typed links turn a plan folder into a small, well-formed graph. Drawn for one feature — and note where the authority sits versus where the data sits.

the node with the most authority in the workflow holds the least data

VERB

dd links

The edges of one target — inbound and outbound. “What depends on this evidence row?” answered from the derived reverse index: links are stored only where authored; the reverse direction is computed and cached, rebuildable at any time — so it can’t lie, can’t churn a target’s sha, and can’t merge-conflict a hub doc. (D11)

VERB

dd build

Run on a file; composes the graph to N link-hops — the doc plus its resolved pressure rows, discharge entries, everything a reader needs in one read. The context packet for agents. Honest frontier rule: when the graph continues past the depth, say so — “7 links beyond the frontier across 3 docs.” Truncation is fine; silent truncation is the sin. (W7)

VERB

dd validate / doctor

The same walk collecting findings instead of content, with a radius dial: depth 0 = this doc; depth 1 = links resolve, basis pins vs current SHAs, render freshness, neighbours’ health; doctor = radius ∞ over every root + sweep-only checks (orphans, unfolded proofs). A finding is owned by the file that must change to fix it. (W8)

THE COMPLETION MECHANIC

Receipt first, state second

1 · orient — the open criterion and its paved proof command are a read
2 · work — implement
3 · prove — run the command; a real invocation, never a narrated one
4 · discharge — entry appends to the execution log; dd check sets the state with the entry linked
5 · gate clears — due criteria: none
6 · depart — nav moves on

GATE DOCTRINE

Binds the agent, never the human

Warn when a linked DD fails validation (someone else’s defect shouldn’t strand travel). Refuse departure while items sit unchecked/blocked — the same rule as today’s chore gate. The human retains the override always: human-skipped, set by a human, receipted with their words, passing the gate but queryable forever.

Honesty note: today’s chore “refusal” is skill doctrine, not CLI enforcement. DD doesn’t claim to close that — it closes the knowability gap: an unmet criterion stops being invisible. due_criteria is computed and printed every turn; enforcement depth stays a shared, explicit question.

The resume test Context compacted mid-phase. Today: the agent re-reads a 300-line plan, guesses which criteria were already satisfied, and its derivation is an opinion. After: orient prints 3 criteria — 2 discharged with receipts, 1 open with its proof command. Zero plan reads; the answer is the same one the previous context had, because it was never in anyone’s context — it was in the document.
10

A portable concept, not a harness feature

DD is a document format + a small library. The harness is its first consumer, not its owner. The same concepts work at three depths of adoption — pick one, move between them, nothing about the files changes.

DEPTH 1

Standalone files

Any git repo or filesystem. Hand-edit the .dd.json, run validate, commit the pair. No harness, no SDK — the format is self-describing, so a lone doc is still checkable, addressable, and render-true. A checklist, an ADR, a runbook: deterministic on day one.

DEPTH 2

Standalone CLI · out of scope, by design possible

The same lib fronted by its own small CLI — validate, render, doctor, build, links — for teams with no harness at all. Deliberately not built now; the architecture keeps the door open.

DEPTH 3

SDK-embedded

A host system builds first-class features on the lib — which is exactly what the harness does: harness plan is a doc-type package (plan schema, section conventions, minted ids, SDD wiring) and the flow spine consumes AC sections through dd-links. Your system’s “plans” could be someone else’s “controls register.”

layering — separate lib inside harness, for now  ┌──────────────────────────────────────────────┐
  consumers      harness verbs (dd·plan·flow) │ standalone CLI (OOS) │ your system
  ├──────────────────────────────────────────────┤

dd-core imports nothing from harness — no envelopes, no error codes, no CLI plumbing. It lives inside the harness repo for now (no premature split; the concepts are the contract), but the boundary is real from day one, so extraction later is a move, not a rewrite.

What this kills — the receipts

Every failure below was found in this repo’s own plan corpus during the 065 survey. Each maps to the specific mechanism that makes it unrepresentable, not merely discouraged.

measured failurekilled by
An AC shipped unverified and nobody noticed — plan 056’s third criterion lost its id to a typo (**n** for **AC-03**), became unnameable, and the review roll-call skipped from 02 to 04 without anything able to object. A completable row cannot exist without an id — validate fails the document before a flow node can ever point at it; the gate enumerates the set, so a hole is a visible open item, not silence.
Checkbox rot — five shipped plans with every plan-doc checkbox still [ ], while the tasks-dossier copy was maintained. Two ledgers, zero reconciliation. One row, one owner, everyone else links. The flow renders the plan’s rows through the link; there is no second checkbox to rot.
Stranded proof plans — backpressure surveys selected proofs that never became task criteria; folding was archaeology (“the plan verb does not auto-read the coverage, so fold the findings in yourself”). The AC’s pressure link column with cardinality 1: an AC with no named proof is a schema error at plan time; “did it get folded in” is an inbound-edge count — an exit code, not an afternoon.
Orphaned surveys — one basis hash ever recorded across 11 surveys, and that lone example is already stale without anyone noticing. Every DD carries a content-sha as a property of the format; citation pins + the contributors ledger make drift a computed warning in checks, not a discipline one plan practised once.
Resume-by-re-inference — an agent landing cold on a node knows a label and a verb; what it owes lives in 300 lines of markdown it must re-read and re-judge. Orient prints the criteria, their states, their receipts, and the open item’s paved command — a read, not an inference, identical for every agent and every session.
