Deterministic
Documents

A new way to write documents that machines can verify and humans can read — where the markdown is a view, the data is the truth, and every claim is an address.

A deterministic document (“DD”) is a document whose source of truth is structured data: a .dd.json file in which every section declares its type, everything addressable carries an id, and the human-readable .dd.md is generated beside it — never authored. Structure is validated, content is hashed, and anything — a plan, a flow node, a check — can point at any section or row and be told when it drifts.

Deterministic Documents

BEAT 1

Imagine a plan

Text blocks, some code, and a table of acceptance criteria with checkboxes. The agent does the work… then checks off the plan. And there it is: the agent has to remember to do this. Nothing prompts the tick, nothing verifies it, nothing notices when it never happens.

BEAT 2

Give the document a schema

In a deterministic document, each section declares a schema. You fill in the data — and the list you read is generated from it. Same reading experience; but now the checkbox is a field, the columns are typed, and validation can refuse nonsense.

BEAT 3

Everything has an address

Because sections and rows are data, each one has a stable address. So a row in one document can link to a row in another file — as a JSON value with a relative path, not prose that hopes. Here one of those checklist items — an acceptance criterion, “AC” for short — points at a row in a second document, the row that says how this criterion will be proven:

BEAT 3B

…and not just documents

Documents are not the only things that can hold an address — anything that can store a short string can. The first thing to use that here is the workflow tracker, the tool that knows which step a piece of work is on: one of its steps carries a single link field, dd_link, aimed at the plan’s checklist. It stores no copy of the items. And because every link is written the same way, a checking tool can walk all of them and confirm each still points at something real.

BEAT 4

The check becomes a gate

Here is the payoff of the checklist being data: other software can read it and rely on it. A workflow system, for example, can point one of its steps at the plan’s checklist and simply refuse to move to the next step while items are still open. When the last item is checked — with its proof attached — the gate opens on its own. Nobody has to remember to update the plan anymore: the workflow won’t move on until the plan says the work is done.

BEAT 5

Then it compounds

Take something you already write: the backpressure survey — the document that works out how each criterion should be proven. Convert it to a deterministic document, and now its rows can be referenced too. Your plan’s checklist points at the exact evidence row that proves each item, and voilà: every promise in the plan names its proof, the proof knows who relies on it, and neither can quietly drift apart again. Keep going and a small web grows around one checklist — a running log records what actually happened when each item was proven, and the task list points in too. None of them copy the checklist; they all just point at it. And because every connection is data, a tool can walk the whole web and tell you the moment any part of it is broken, missing, or out of date.

BEAT 6

Two graphs, one bridge

Step back and there are two separate webs here, kept in separate files on purpose. One is the knowledge graph — what you know and can prove: plans, evidence, logs. The other is the workflow graph — where work is and what may move next. Neither stores the other’s data: the workflow holds no checklist text, the documents hold no notion of “current step.” They meet at exactly one typed link — and across it, the workflow computes its gates from what the knowledge can prove. (decided · D12)

01

The problem: coding in markdown

Plenty of markdown does more than describe things — it carries working state: checklists that say what is done, criteria that say what must be true, notes that say what was proven. That makes it a program written in a language with no parser: nothing can read it back and check it. Every failure below is a real one, counted in the plan documents of the codebase this idea grew out of.

ROT 1

Linting checks form, not meaning

Markdown can be linted — this repo does. But a linter validates formatting: heading levels, list style, spacing. It can never say “this table is the acceptance criteria,” “that column only allows these values,” or “a required section is missing.” The document’s meaning is re-inferred by every reader, every session — and nothing detects a wrong inference.

ROT 2

Checkboxes rot

- [x] handles declined cards has no id, no author, no timestamp, no reason. Measured: five shipped plans whose plan-doc checkboxes are all still [ ] — while a second copy in the tasks dossier was maintained. Two ledgers, nothing reconciles them.

ROT 3

References drift silently

A backpressure survey — the document that works out how each criterion should be proven — is written against a plan as it stood at one moment. Of 11 such surveys, exactly one recorded which version of the plan it had actually read (a content fingerprint, or SHA, taken at the time) — and that one is now stale: the plan changed afterwards, and nothing noticed. The single document that tried to do it properly was quietly left citing a version that no longer exists.

ROT 4

Nothing is addressable, so everything is copied

You cannot say “criterion 3 of phase 2” in a form a tool can look up — so every place keeps its own version: the workflow tracker keeps none of the criteria at all, the plan keeps them as prose, and the task list keeps a paraphrase. In one real plan, a criterion’s label was lost to a typo (**n** typed instead of **AC-03**): the criterion could no longer be named, so nothing could demand proof of it, and it shipped unverified.

The measured baseline Counted across 54 of those workflow files: not one carries any field saying what the work must achieve · exactly one ever recorded the version of the document it was based on (and that record is now stale) · the per-step instructions are byte-for-byte identical boilerplate (“done when the acceptance criteria are met”) across three generations of the tooling. An agent picking work back up gets a step name and a command to run — never what it owes, or how that would be proven.

Why the pair matters Humans and GitHub read the .md; tools and agents read the .json. Because the .md is a build artifact, a stale or hand-edited copy isn’t “reconciled” — it is detected (the checker reports the generated file as out of date with its data) and regenerated. One representation, two views, zero divergence.
Write posture — decided (D1) Some formats can only be written through their own tool: you ask the tool, and the tool edits the file. A DD is not like that. It is a validated file format, so any person, agent, or tool may open the .dd.json and edit it directly — dd validate, dd doctor and regeneration are what keep every edit honest, whoever made it. That is exactly what lets a DD stay useful in a repo that has none of this tooling installed.
03

Two id regimes: addresses vs records

Everything in a DD is addressable, but sections and rows need opposite kinds of identity. The rule that picks the regime: what should break when this thing is renamed?

SECTIONS · STABLE BY CONVENTION

Sections are addresses

A section id is derived, never invented — type + name, mechanically:

type: plan-phase-ac   name: "Phase 2"
        └──────── slug + join ────────┘
   id: plan-phase-ac.phase-2
 full: plan.dd.json#plan-phase-ac.phase-2/row:ac-4b1c

The same phase carries the same id in every plan file in the repo, forever — semantic, greppable, and predictable before the file even exists, which matters more than it sounds. A workflow step can be written to point at “phase 2’s criteria” of a plan nobody has authored yet, and the checker will report that address as pointing at nothing, instead of the pointer silently meaning nothing at all.

Renaming changes the address — so renaming is a first-class operation: dd rename-section recomputes the id and rewrites every inbound link across the repo in one transaction (decided · D8).

ROWS · UNIQUE, BORN ONCE

Rows are records

An element id — ac-4b1c, bp-7f3a, el-0042 — is minted once at creation and never re-derived from content. Sharpen an AC’s wording from “handles declined cards” to “a declined card returns a typed error” and it is the same criterion: it keeps its state, its evidence links, and every inbound reference.

If row ids were derived from text, a clarifying edit would be a delete-plus-create — silently discarding completion state and orphaning every link. That is checkbox rot with extra steps.

One consequence worth saying twice “AC-3 of phase 2 of the checkout plan” is now a resolvable name: plan.dd.json#plan-phase-ac.phase-2/row:ac-4b1c. Because it can be named, it can be linked; because it can be linked, it never needs to be copied — and the copies were where every drift problem in §01 lived.
04

Section primitives

There can be as many kinds of document as you like — a plan, a proof survey, a run log, a decision record — and teams can add their own. Underneath, though, there are only a few section shapes, and that set is deliberately closed: a shape is something the tooling knows how to store, check, render, and let a workflow refuse to move past. Two documents as different as a plan’s criteria list and a survey’s evidence list are different kinds built on the same shape.

PRIMITIVE

free-text

Prose in a named, addressable slot. Most of a plan stays prose — it just stops being the container that structure has to be guessed out of. Validate: present / non-empty.

PRIMITIVE

list

A flat enumeration with no state — goals, non-goals, notes. Plain strings, no ids. The rule (decided · D13): an element earns an id when it carries state or is a link target; wanting to link to a list item means you needed a completable section.

PRIMITIVE

completable-list

Tickable items, each with an id, a state, and links to its evidence — this is the shape an acceptance-criteria checklist uses, and the shape a workflow can be told to wait on before it lets work move to the next step. An item marked complete with no evidence attached is a validation error, not a style nit: an unevidenced tick cannot be expressed in a valid document at all.

PRIMITIVE

completable-table

Same completion behaviour, richer rows: columns carry declared types — string · int · state · link. A link column also declares what it is allowed to point at (“a row in a proof-survey document”) and how many it must have (“every criterion must name its proof”). The wiring is then enforced by the document’s own schema, rather than by somebody remembering to check for it in review (shapes illustrative until W3/W6 close).

PROPOSED

log (append-only)

Entries with born-once ids that may be added but never mutated or deleted — enforced by validate, not convention. The execution log becomes this (decided · D3): the durable trail AC rows point their discharge links into.

PROPOSED

record · include

record: a small typed header of key/value facts — owner, linked workflow, counts — replacing the bolded-label-and-colon fake tables people hand-write today. include: show another document’s section in place, by address, storing a pointer and a fingerprint rather than a copy of the content (§6).

Completion is a state, not a boolean (decided · D4)

A checkbox can only lie by omission. A state can tell the truth about why it isn’t done — and the research behind this page found exactly that damage in the existing workflow files: one status (assumed) doing double duty for “not yet” and “never ran, no record”.

□ unchecked — open; holds the gate ✓ checked — proven; passes ⊘ blocked — can’t proceed; holds, loudly ◈ human-skipped — waived by a human, receipted; passes but queryable forever

Simple bool columns still exist for plain facts — state is for things a workflow gates on. Exact vocabulary is an open workshop item (W2), including who may set human-skipped (human-only, receipted).

Open workshop item — W1 · render adapters for custom types The built-in column types come with their own display rules. But teams will invent their own — a risk rating, a currency, a severity — and something has to decide how those look in the generated markdown. The likely answer: whoever defines the document type also ships the display rule for its own column types, plus a mandatory honest fallback for anything unrecognised — print the raw value and the name of its type; never crash, never silently show a blank cell. Flagged for its own workshop.
05

The AC row is a signpost, not a container

Imagine your plan has an acceptance criterion in it: “a declined card returns a typed error.” Where should everything about that criterion live? Not on the row. The row stays small — an id, the sentence itself, its state, maybe a short note — plus two links pointing in opposite directions in time: one at how it’s meant to be proven, one at how it actually was. All the heavy detail lives at the other end of those links, in the documents that own it. The row is a signpost, not a filing cabinet. (decided · D2)

← PRESCRIPTIVE · pressure

backpressure.dd.json

What must be proven, and how — decided before the work starts. Row bp-7f3a says this criterion is proven by actually running something (rather than by reading the code or eyeballing the result), names the exact command that does it — npm test -- decline-path — and records what that proof is worth: machine-checkable, high confidence.

The link also stores a fingerprint of the evidence document as it read at the moment it was cited — a basis pin. If how the criterion is meant to be proven changes later, that fingerprint no longer matches, and the citation shows up as stale rather than quietly meaning something else (§6).

DEMONSTRATIVE · discharge →

execution-log.dd.json

How it was actually discharged — appended during work. Entry el-0042: the command run, its exit and output digest, timestamp, actor, artifacts (entry shape illustrative — W3). Append-only by validation (a mutated prior entry fails dd validate).

An append-only trail like this is normally kept by discipline — remember to log what you ran, remember never to edit it afterwards. Here it comes from the format: the document simply cannot be valid if a past entry was changed.

Validation has teeth in both directions A criterion with no link to how it will be proven is unproven by design — the schema requires that link, so the document fails validation while you are still writing the plan. A criterion ticked complete with no link to how it actually was proven is unproven in fact — the repo-wide check catches that at the moment you claim to be done. Neither answer needs anyone to go digging through history: both are just counting links the documents already declare.
06

Links, and the two ways of tracking change

A link here is not a hyperlink you click — it is a value in the data, made of three parts: a path to another file, the id of a section inside it, and the id of a row inside that. It resolves the same way from anywhere in the repo. There are two reasons to point at something, and they want opposite behaviour when the target changes: sometimes you want to always see the latest version, and sometimes you want to be told the moment it stops being what you agreed to.

  └── relative path (repo-internal) ──┘   └─ stable section ─┘  └─ born-once row ─┘
A WINDOW · transclusion

Live, and it can never drift

The workflow’s step “shows” the plan’s criteria section. There is no copy — it displays the plan’s own rows through the link, live. Tick an item in the plan and the workflow sees it immediately, because there is only one list.

Keeping the readable markdown fresh is handled mechanically: each time a file is generated, it records which documents fed it and a fingerprint of each one. If an input has changed since, the generated file is known to be out of date and is simply rebuilt — automatically when a document is edited, by a watcher when someone edits by hand, and as a last backstop when the project’s checks run. Auto-refreshing is always safe here: regenerating a view of the truth cannot make it lie. (D9)

A CITATION · reference + basis pin

Pinned, and drift is the signal

AC-04 says “my proof is bp-7f3a.” That is a claim about what bp-7f3a said at the time — so the link records the target’s content-sha at citation: the basis pin. Someone later weakens that evidence row? The link still resolves, everything still looks fine — but the pin no longer matches.

Never auto-refreshed. The pin means “someone confirmed this pairing” — only a re-verify (fine, refresh the pin), re-point (cite better evidence), or contest (the target’s change was wrong) moves it. A tool silently updating it would be vouching for something nobody looked at.

How drift is “announced” — it isn’t Nothing pushes a notification. The fingerprint just makes drift computable, and the things that already run at useful moments will say so: the repo-wide checker, which runs alongside the project’s other checks, so CI fails on a stale citation exactly like a failing test; the agent’s start-of-turn status readout, where a criterion whose cited proof has drifted prints as checked (stale); and the renderer, which puts a visible marker beside the link in the generated markdown. Same trust model as a checksum on a download: verified at the moment of use, which is the only moment that matters.
07

The graph, and the verbs that walk it

Typed links turn a plan folder into a small, well-formed graph. Drawn for one feature — worth noticing as you read it: the thing that decides whether work may move forward stores almost nothing itself.

the step that decides whether work may proceed holds the least data of anything here

VERB

dd links

The edges of one target — inbound and outbound. “What depends on this evidence row?” is computed, never stored: links live only where authored, and the reverse direction comes from a quick scan of the current folder and below when you ask interactively, and the full-repo sweep when the project’s checks run. One copy of the truth, no index to go stale, nothing to merge-conflict. (D11)

VERB

dd build

Point it at a file and it follows the links outward a set number of steps, returning the document together with what it points at — the proof rows, the log entries — so a reader gets the whole picture in one read instead of chasing files. That is what you hand an agent so it does not have to go hunting. Honest frontier rule: when there is more graph past the depth you asked for, it says so — “7 links beyond the edge of this view, across 3 documents.” Cutting the view short is fine; cutting it short silently is the sin. (W7)

VERB

dd validate / doctor

The same walk, collecting problems instead of content, with a dial for how far to look. Look at one document only and you get schema problems. Look one step further out and you also get: do its links resolve, do the fingerprints it recorded still match the files today, is the generated markdown up to date, are its neighbours healthy. Turn the dial all the way up and it sweeps the whole repo, which additionally catches what is only visible from above — documents nobody points at, proofs that were chosen but never picked up. Each finding is owned by the one file that has to change to fix it. (W8)

How a workflow tracker uses it

The workflow tracker used here — “the flow” — keeps the list of steps that work moves through. Today a step knows almost nothing about the requirements: it has a name, a command to run, and the same boilerplate line every other step has, “done when the acceptance criteria are met.” Which criteria? It cannot say. After: the step carries one pointer at the plan’s checklist, and “what do I still owe?” stops being a judgement call and becomes something you simply read.

THE COMPLETION MECHANIC

Receipt first, state second

1 · look — the agent’s start-of-turn readout already shows the open criterion and the exact command that proves it
2 · work — implement it
3 · prove — run that command for real; claiming it passed is not the same as running it
4 · record — the run appends an entry to the log; dd check then sets the item’s state with that entry linked to it
5 · the block lifts — nothing is outstanding any more
6 · move on — the workflow allows the next step

GATE DOCTRINE

Binds the agent, never the human

Warn if a linked document is itself invalid — somebody else’s broken file should not strand you where you are. Refuse to let the workflow advance while items are still open or blocked; that is the same rule the existing routine-task check already applies. The human keeps the override, always: an item can be marked human-skipped — only by a person, only with their reason recorded — which lets the work move on while leaving the skip permanently visible to anyone who asks.

Honesty note: today that refusal is a rule the agent is told to follow, not something the CLI enforces — an agent could ignore it. Deterministic documents do not claim to fix that. What they fix is knowing: an unmet criterion stops being invisible, because the count of what is still open is computed and printed at the start of every turn. How hard the refusal should bite stays a separate, deliberate question.

The resume test An agent’s working memory is cleared and summarised partway through a phase — routine, and unavoidable. Today: it re-reads a 300-line plan, works out for itself which criteria look satisfied, and that working-out is an opinion. After: its start-of-turn readout prints 3 criteria — 2 already proven, each with the run that proved it, and 1 still open with the command that will. No plan reading at all, and the answer is identical to the one the previous context had, because it never lived in anyone’s context — it lived in the document.
10

A portable concept, not a harness feature

DD is a document format + a small library. The harness is its first consumer, not its owner. The same concepts work at three depths of adoption — pick one, move between them, nothing about the files changes.

DEPTH 1

Standalone files

Any git repo or filesystem. Hand-edit the .dd.json, run validate, commit the pair. No harness, no SDK — the format is self-describing, so a lone doc is still checkable, addressable, and render-true. A checklist, an ADR, a runbook: deterministic on day one.

DEPTH 2

Standalone CLI · out of scope, by design possible

The same lib fronted by its own small CLI — validate, render, doctor, build, links — for teams with no harness at all. Deliberately not built now; the architecture keeps the door open.

DEPTH 3

SDK-embedded

A host system builds first-class features on top of the library — which is exactly what the harness does here. Its plan command is a document-type package: it owns the plan’s schema, its section naming conventions, how ids are minted, and how plans slot into the wider planning method. The workflow tracker then reads a plan’s criteria sections through these links. What this system calls “plans”, another could call a controls register — same machinery underneath.

What this kills — the receipts

Every failure below was found by going through the plan documents of one real codebase and checking each claim against the files themselves — a survey of seven plans first, then per-claim verification across the wider set (the typo, the stale fingerprint, and the 54-file count all come from that verified pass). Each is paired with the specific mechanism that makes it unrepresentable, rather than merely discouraged.

measured failurekilled by
An AC shipped unverified and nobody noticed — plan 056’s third criterion lost its id to a typo (**n** for **AC-03**), became unnameable, and the review roll-call skipped from 02 to 04 without anything able to object. A completable row cannot exist without an id — validate fails the document before a flow node can ever point at it; the gate enumerates the set, so a hole is a visible open item, not silence.
Checkbox rot — five shipped plans with every plan-doc checkbox still [ ], while a second copy of the same list, kept alongside the tasks, was maintained. Two ledgers, zero reconciliation. One row, one owner, everyone else links. The flow renders the plan’s rows through the link; there is no second checkbox to rot.
Proof plans that went nowhere — surveys carefully chose how each criterion would be proven, and then nobody carried those choices into the actual task list. Finding out whether it had happened meant reading old documents side by side. The tooling’s own instructions said as much: the planning command does not read the survey for you, so copy the findings across yourself. Every criterion must name its proof — the schema requires exactly one such link, so a criterion with nothing named fails validation while the plan is still being written. And “did those choices actually get picked up?” becomes a count of the links pointing in: an exit code, not an afternoon.
Orphaned surveys — one basis hash ever recorded across 11 surveys, and that lone example is already stale without anyone noticing. Every DD carries a content-sha as a property of the format; citation pins + the contributors ledger make drift a computed warning in checks, not a discipline one plan practised once.
Resume-by-re-inference — an agent landing cold on a node knows a label and a verb; what it owes lives in 300 lines of markdown it must re-read and re-judge. The agent’s start-of-turn readout prints the criteria, the state of each, the run that proved the finished ones, and the exact command waiting on the open one — something it reads, not something it works out, and identical for every agent and every session.
