# 065 Deterministic Documents — workshop notes (running)

Captured from the Jordan ↔ silkworm concept Q&A, 2026-08-03. Source of intent: `initial-brief.md`. These are pre-plan decisions and open items; the plan verb will formalise them.

## Decisions so far

- **D1 — Write posture**: `.dd.json` is a *validated file format*, not a CLI-mediated store. Anyone/any tool may edit; `dd validate` / `dd doctor` / render are the contract. (Diverges deliberately from the-flow's hard single-writer.) The rendered `.dd.md` remains generated-only.
- **D2 — AC rows are signposts, not containers**: an AC row carries id, description, completion state, a short free-text note, and typed links: → backpressure DD row (*prescriptive*: what pressure is needed, how to prove) and → execution-log DD entry (*demonstrative*: how it was proven — link name `proven_by`, renamed from "discharge" by Jordan 2026-08-03). Heavy evidence detail lives at the link targets, not on the row.
- **D3 — Execution log becomes a DD**: append-only entries with unique ids so AC rows (and others) can link to the specific discharging entry. Append-only enforced by validation (an edit that mutates/deletes a prior entry fails validate).
- **D4 — Completion is a state, not a boolean**: something like `unchecked / checked / blocked / human-skipped` (final vocabulary TBD). `human-skipped` passes the nav gate but remains queryable forever; `blocked`/`unchecked` hold it. Simple `bool` columns still exist for plain cases.
- **D5 — The flow spine links, never copies**: nodes reference plan AC sections by stable address (`{file, section}`); ticks/state live in the plan DD. Links-on-links, graph style.
- **D6 — Graph tooling is first-class**: alongside `dd doctor` (integrity: resolution, cardinality, drift, acyclic includes), a graph family — explore/traverse/visualise the typed link graph (e.g. `dd graph`, `dd links <target>` for inbound/outbound edges).
- **D7 — Portability**: dd-core is a library (injected ports, no harness imports), harness is the first consumer; standalone CLI is out of scope for now but the architecture must keep it possible. Adoption spectrum (Jordan): depth 1 = standalone `.dd.json` files in any repo/filesystem (hand-edit + validate); depth 2 = standalone CLI (OOS); depth 3 = SDK-embedded, host systems building first-class features on the lib (harness/plans is the exemplar). Build posture: a cleanly-separated lib *inside* the harness repo for now — real boundary, no premature split; the concepts are the contract.
- **D8 — Renames**: section ids stay convention-derived; `dd rename-section` is a first-class verb that recomputes the id and rewrites every inbound link repo-wide in one transaction (resolves W4; alias tombstones remain an option for external references).
- **D9 — Contributors ledger + cascade regen** (resolves W5's mechanics): a consumer's `.dd.json` holds only pointers; its generated `.dd.md` is where transcluded content materializes. At render time the doc records a contributors manifest (path + content-hash of every input doc). Staleness = recompute vs manifest; dependents' `.dd.md` auto-regenerate on contributor edit (CLI path, watcher for hand-edits, `checks` backstop). Two hash ledgers with opposite refresh rules: contributors manifest (view freshness — auto-refresh always correct, eager + silent) vs citation basis pin (decision validity — never auto-refreshed; re-verify / re-point / contest only).
- **D10 — Title**: the concept overview HTML is "AI Substrate presents — Deterministic Documents".
- **D12 — Two graphs, one bridge (Jordan: "two graphs, one knowledge, one workflow… wf graph can create wf gates based on kb concepts")**: knowledge and workflow are SEPARATE graphs in separate stores — the knowledge graph (DDs: plans, backpressure, execution logs — what is known and proven) and the workflow graph (the flow spine — where work is and what may move). Neither pollutes the other: the spine holds no knowledge (no criteria text, no tick state), DDs hold no nav state. The bridge is typed deterministic linkage: a workflow node's dd_link derives its **gate** from knowledge-graph state (completable-section satisfaction), so workflow gates are *computed from* knowledge concepts, never copied into the workflow. This is the graph-engineering two-halves model (knowledge graphs = memory, task graphs = execution) realized deterministically.

- **D11 — Links are source-only; reverse lookups are computed, nothing stored (RULED by Jordan 2026-08-03)**: links live only where authored (the pointing doc). No inbound-edge fields in targets AND no persisted reverse-index file ("i dont like storeing more data like 'little indexes'"). "Who points at me" is answered by scanning: interactive verbs scan a local scope (current folder and below — "scan local parents down probably okay"); anything broader is doctor's full-repo sweep inside `checks` ("if broader then checks will reveal it later"). Avoids sha churn on citation, hub-doc merge conflicts, and lying caches; a cache may be added later purely as an optimization (a rebuildable view), never as semantics.
- **D13 — Element ids follow state/linkability (RULED by Jordan 2026-08-03)**: an element gets a born-once id when it carries state or can be a link target (checklist items, table rows, log entries); plain list items (goals, notes) are id-less strings ("i can't see why plain list woudl need ids"). Wanting to link to a bullet is the signal to promote the section to a completable list. Refines the brief's every-element-has-an-id line; resolves raven finding 2.
- **D14 — Schemas are named packages, by reference, resolved by convention (RULED by Jordan 2026-08-03, captured by PM koala in the koala session; recorded by silkworm; full capture: koala's `schema-ruling-capture.md`)**: a `.dd.json` *names* its schema, never embeds it — no inline mode (supersedes the brief's "contain their schema" line; resolves W6 by supersession). Identity is a fully-qualified two-segment name `package/schema` (e.g. `builder/plan`; no `-schema` suffixes — "we know they're schemas"; no bare short form). Layout: `.dd/schemas/<package>/<schema>/`, one self-describing schema file per folder (name + description in-file, no sidecar; the folder is the natural later home for W1 render adapters). Resolution order, first hit wins: doc's own folder (ultimate override) → `<gitroot>/.dd/schemas/` → `.harness/.dd/schemas/` → `~/.dd/schemas/`, scanning children under each root. Clashes are loud: duplicate qualified name within a root = hard error; cross-root shadowing and same-folder overrides are surfaced by `dd doctor` (winner + shadowed); `dd schema list` shows name/description/source/shadowed (`dd schema show` PM-proposed, unruled). Evolution is a breaking change: docs float live against the current schema — no versions in refs, no basis pin; a tightened schema fails its docs immediately and doctor reports the blast radius. An unresolvable ref is a hard validate ERROR. No fixtures in schema packages — validator correctness belongs to dd's own central unit tests (Jordan ruled against the PM recommendation; recorded as considered-and-rejected). Small loose end for W9: confirm hierarchy above package folders is organization-only, never part of the name.

## Open items (to workshop)

- **W8 — validate-radius model (proposed by Jordan)**: `dd validate` runs on a file (same file-level invocation rule as build) and gains a configurable depth — depth 0 = this doc (schema/structure/ids/evidence, the manual-edit front line); depth 1 default = outbound links resolve + basis pins vs current target SHAs + contributors manifest freshness ("rebuild needed") + neighbors' depth-0 health; doctor = the same engine at radius ∞ over all roots (+ sweep-only checks: orphans, unfolded proofs, reverse-index verify). `build` and `validate` are one graph walk collecting different things (content vs findings). Rule to lock: a finding is owned by the file that must change to fix it — a broken neighbor surfaces on my run but fails only its own doc. Watcher: on save, validate changed doc + inbound neighbors at depth 1 (continuously-warm doctor).
- **W7 — `dd build` (proposed by Jordan)**: take an input doc (file-level root — sub-address roots rejected as unneeded; invocation unit is the file) and build out the composed view to N link-hops deep, warning honestly when the graph continues past the cutoff (frontier report: links/docs beyond depth, deepest chain). Key design questions: output ephemerality (context packet vs persisted render governed by contributors ledger — never a second source of truth), depth semantics per edge kind (transclusions always resolve; citation hops count), edge filtering (`--follow pressure,discharge`), inbound builds via the derived index. Primary use cases: agent context loading (one read instead of link-chasing), review packets, briefings.

- **W1 — Custom types × render adapters**: built-in column/field types (string, int, bool, link, completion-state) render natively. Users adding complex types in their own custom DDs need a renderer story: registered per-type render adapters shipped by doc-type packages? Mandatory honest fallback for unknown types (raw value + type tag, never crash/blank)? How adapters compose for `.dd.md`, graph views, and future HTML renders. Per D14, a schema's package folder (`.dd/schemas/<package>/<schema>/`) is the natural shipping home for its adapters/templates. **Flagged by Jordan for a later workshop; must appear in the concept infographic.**
- **W2 — Completion-state vocabulary**: exact enum + which states gate nav vs pass-with-record; who may set `human-skipped` (human-only, receipted).
- **W3 — Evidence-entry shape on the execution-log DD**: entry kinds (command-run / artifact / prose / attestation) now or later; minimum viable = append-only entries with links.
- ~~W4 — Section renames~~ — **resolved as D8** (`dd rename-section` first-class).
- ~~W5 — Link basis pins~~ — **resolved as D9** (role-determined: transclusions float live under the contributors ledger; citations pin a basis, drift surfaces via doctor/orient/render, never auto-refreshed).
- ~~W6 — Schema-in-file depth~~ — **resolved by supersession as D14** (by-reference named schema packages; no inline mode).
- **W10 — `done_when` granularity on plan task rows (surfaced by the plans exemplar, 2026-08-03)**: in real plans (e.g. 063) a task's "Success Criteria" cell is really 3–8 distinct assertions packed into one prose string. Schema choice: keep `done_when` as one text field (cheap, matches today's plans) vs a nested completable-list per row (each assertion individually checkable, provable, and linkable to its own evidence). Decides how fine-grained backpressure/`proven_by` evidence can attach. See `exemplar-plans-as-dd.md`.
- **W9 — Addressing workshop (Jordan: "we should get a good solid workshop done on addressing when ready")**: the full address grammar as a first-class design surface — canonical syntax (`path#section-id/kind:element-id`, compact string vs object form, normalization on write); section-id derivation rules (slugging, case/whitespace/punctuation normalization, singleton reduction, uniqueness-within-file); element-id minting (prefix conventions, length, collision scope); rename/alias semantics interplay (D8 tombstones); how addresses map to `.dd.md` anchors (GitHub heading anchors vs opt-in HTML row anchors); address stability guarantees a consumer may rely on; reserved room for a future cross-repo scheme. Addressing is load-bearing for everything (links, spine dd-links, build/validate walks, reverse index) — deserves its own session before the plan locks the grammar. **D14 adds a second reference kind to this workshop's scope**: schema refs are qualified NAMES resolved by root-scan, distinct from doc links (relative PATHS) — two kinds, two resolution rules, to be specified side by side; also confirm folder hierarchy above a schema package is organization-only, never part of the name.


## Validation lessons (recorded 2026-08-03, from the infographic's own review cycle)

One artifact, three instruments, each blind to the others' defect class — worth carrying into DD's design, since DD proposes exactly these tiers:

1. **Structure** — a parse check caught an eaten `>` and ~790 lines nested in an unclosed `<figure>`. It cannot see meaning.
2. **Appearance** — headless-render screenshots caught overlaps and clipping. They could not see the structural break at all, because the browser silently error-recovers broken markup (and they manufactured two false defects of their own: sips center-crop at offset 0; the 500px window floor).
3. **Semantics** — a human who knows the model caught a diagram edge asserting a FALSE relationship (`implements ac-4b1c` drawn into the execution log when that row lives in the plan). It rendered perfectly, parsed perfectly, and was wrong. Neither machine tier could ever have flagged it.

Mapping to DD: `dd validate` is tier 1, renders are tier 2 — and the design should stay honest that tier 3 (does the content say something TRUE?) remains review by someone who knows the model. Deterministic documents make tiers 1–2 cheap and mechanical precisely so human attention can be spent on tier 3.
