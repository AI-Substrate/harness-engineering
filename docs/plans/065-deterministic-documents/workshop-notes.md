## Standing design rule — measure everything against this first

> **R-elegance (RULED by Jordan 2026-08-03): "we must be elegant and not over-engineer."**

Every schema shape, verb, and workshop outcome below is judged against this before anything else. Where a design has a small version and a general version, the small one wins unless the general one has been *earned* by a real need. Several dispositions below are direct applications of it (W1's adapter is a function, not a framework; W2 ships defaults rather than a vocabulary system; W3 keeps entries free-text).

## Decisions so far

- **D1 — Write posture**: `.dd.json` is a *validated file format*, not a CLI-mediated store. Anyone/any tool may edit; `dd validate` / `dd doctor` / render are the contract. (Diverges deliberately from the-flow's hard single-writer.) The rendered `.dd.md` remains generated-only.
- **D2 — AC rows are signposts, not containers**: an AC row carries id, description, completion state, a short free-text note, and typed links: → backpressure DD row (*prescriptive*: what pressure is needed, how to prove) and → execution-log DD entry (*demonstrative*: how it was proven — link name `proven_by`, renamed from "discharge" by Jordan 2026-08-03). Heavy evidence detail lives at the link targets, not on the row.
- **D3 — Execution log becomes a DD**: append-only entries with unique ids so AC rows (and others) can link to the specific discharging entry. Append-only enforced by validation (an edit that mutates/deletes a prior entry fails validate).
- **D4 — Completion is a state, not a boolean**: something like `unchecked / checked / blocked / human-skipped` (final vocabulary TBD). `human-skipped` passes the nav gate but remains queryable forever; `blocked`/`unchecked` hold it. Simple `bool` columns still exist for plain cases.
- **D5 — The flow spine links, never copies**: nodes reference plan AC sections by stable address (`{file, section}`); ticks/state live in the plan DD. Links-on-links, graph style.
- **D6 — Graph tooling is first-class**: alongside `dd doctor` (integrity: resolution, cardinality, drift, acyclic includes), a graph family — explore/traverse/visualise the typed link graph (e.g. `dd graph`, `dd links <target>` for inbound/outbound edges).
- **D7 — Portability**: dd-core is a library (injected ports, no harness imports), harness is the first consumer; standalone CLI is out of scope for now but the architecture must keep it possible. Adoption spectrum (Jordan): depth 1 = standalone `.dd.json` files in any repo/filesystem (hand-edit + validate); depth 2 = standalone CLI (OOS); depth 3 = SDK-embedded, host systems building first-class features on the lib (harness/plans is the exemplar). Build posture: a cleanly-separated lib *inside* the harness repo for now — real boundary, no premature split; the concepts are the contract.
- **D8 — Renames**: section ids stay convention-derived; `dd rename-section` is a first-class verb that recomputes the id and rewrites every inbound link repo-wide in one transaction (resolves W4; alias tombstones remain an option for external references).
- **D9 — Contributors ledger + cascade regen** (resolves W5's mechanics): a consumer's `.dd.json` holds only pointers; its generated `.dd.md` is where transcluded content materializes. At render time the doc records a contributors manifest (path + content-hash of every input doc). Staleness = recompute vs manifest; dependents' `.dd.md` auto-regenerate on contributor edit (CLI path, watcher for hand-edits, `checks` backstop). Two hash ledgers with opposite refresh rules: contributors manifest (view freshness — auto-refresh always correct, eager + silent) vs citation basis pin (decision validity — never auto-refreshed; re-verify / re-point / contest only).
- **D10 — Title**: the concept overview HTML is "AI Substrate presents — Deterministic Documents".
- **D12 — Two graphs, one bridge (Jordan: "two graphs, one knowledge, one workflow… wf graph can create wf gates based on kb concepts")**: knowledge and workflow are SEPARATE graphs in separate stores — the knowledge graph (DDs: plans, backpressure, execution logs — what is known and proven) and the workflow graph (the flow spine — where work is and what may move). Neither pollutes the other: the spine holds no knowledge (no criteria text, no tick state), DDs hold no nav state. The bridge is typed deterministic linkage: a workflow node's dd_link derives its **gate** from knowledge-graph state (completable-section satisfaction), so workflow gates are *computed from* knowledge concepts, never copied into the workflow. This is the graph-engineering two-halves model (knowledge graphs = memory, task graphs = execution) realized deterministically.

- **D11 — Links are source-only; reverse lookups are computed, nothing stored (RULED by Jordan 2026-08-03)**: links live only where authored (the pointing doc). No inbound-edge fields in targets AND no persisted reverse-index file ("i dont like storeing more data like 'little indexes'"). "Who points at me" is answered by scanning: interactive verbs scan a local scope (current folder and below — "scan local parents down probably okay"); anything broader is doctor's full-repo sweep inside `checks` ("if broader then checks will reveal it later"). Avoids sha churn on citation, hub-doc merge conflicts, and lying caches; a cache may be added later purely as an optimization (a rebuildable view), never as semantics.
- **D13 — Element ids follow state/linkability (RULED by Jordan 2026-08-03)**: an element gets a born-once id when it carries state or can be a link target (checklist items, table rows, log entries); plain list items (goals, notes) are id-less strings ("i can't see why plain list woudl need ids"). Wanting to link to a bullet is the signal to promote the section to a completable list. Refines the brief's every-element-has-an-id line; resolves raven finding 2.
- **D14 — Schemas are named packages, by reference, resolved by convention (RULED by Jordan 2026-08-03, captured by PM koala in the koala session; recorded by silkworm; full capture: koala's `schema-ruling-capture.md`)**: a `.dd.json` *names* its schema, never embeds it — no inline mode (supersedes the brief's "contain their schema" line; resolves W6 by supersession). Identity is a fully-qualified two-segment name `package/schema` (e.g. `builder/plan`; no `-schema` suffixes — "we know they're schemas"; no bare short form). Layout: `.dd/schemas/<package>/<schema>/`, one self-describing schema file per folder (name + description in-file, no sidecar; the folder is the natural later home for W1 render adapters). Resolution order, first hit wins: doc's own folder (ultimate override) → `<gitroot>/.dd/schemas/` → `.harness/.dd/schemas/` → `~/.dd/schemas/`. **Folder hierarchy above a package folder is organization-only** (addendum, ruled by Jordan 2026-08-03): resolution deep-scans each root until the qualified name is found — "it just deep scans until found" — so however you nest your schema folders, that structure never becomes part of the name. Clashes are loud: duplicate qualified name within a root = hard error; cross-root shadowing and same-folder overrides are surfaced by `dd doctor` (winner + shadowed); `dd schema list` shows name/description/source/shadowed, and `dd schema show <package>/<schema>` gives the full detail view (RULED in the addendum below) — **both must print the resolved schema file path** ("should show paths to the schema file they resolved"). Evolution is a breaking change: docs float live against the current schema — no versions in refs, no basis pin; a tightened schema fails its docs immediately and doctor reports the blast radius. An unresolvable ref is a hard validate ERROR. No fixtures in schema packages — validator correctness belongs to dd's own central unit tests (Jordan ruled against the PM recommendation; recorded as considered-and-rejected). *Addendum ruled by Jordan 2026-08-03, relayed via koala: deep-scan resolution (folded in above) and `dd schema show` promoted from PM-proposed to ruled, with both discovery verbs printing resolved paths. No loose ends remain on D14.*

- **D15 — `dd` ships its own docs system (RULED by Jordan 2026-08-03, surfaced by the W1 discussion; PM capture: `research/workshop-dispositions-capture.md`)**: the `dd` command carries help docs the same way the harness does — `dd docs list` and `dd docs get <doc>`. One of those docs is mandatory and named: **"how to add a new schema, including its md adapter"**. This is what makes D14's schema packages and W1's adapters usable by someone who was not in these sessions — the mechanism is only as portable as its instructions.
- **D16 — `dd link resolve` (RULED as a verb by Jordan 2026-08-03, arising from W3)**: take a link's text and report the document + section it points at. It is the interactive face of the resolver `validate` already needs — one engine, two callers — and sits in D6's graph family beside `dd links <target>` (inbound/outbound edges).

## Validation lessons (recorded 2026-08-03, from the infographic's own review cycle)

One artifact, three instruments, each blind to the others' defect class — worth carrying into DD's design, since DD proposes exactly these tiers:

1. **Structure** — a parse check caught an eaten `>` and ~790 lines nested in an unclosed `<figure>`. It cannot see meaning.
2. **Appearance** — headless-render screenshots caught overlaps and clipping. They could not see the structural break at all, because the browser silently error-recovers broken markup (and they manufactured two false defects of their own: sips center-crop at offset 0; the 500px window floor).
3. **Semantics** — a human who knows the model caught a diagram edge asserting a FALSE relationship (`implements ac-4b1c` drawn into the execution log when that row lives in the plan). It rendered perfectly, parsed perfectly, and was wrong. Neither machine tier could ever have flagged it.

Mapping to DD: `dd validate` is tier 1, renders are tier 2 — and the design should stay honest that tier 3 (does the content say something TRUE?) remains review by someone who knows the model. Deterministic documents make tiers 1–2 cheap and mechanical precisely so human attention can be spent on tier 3.
