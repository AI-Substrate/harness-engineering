## Part 1 — `harness dd` verb table

Every verb resolves its document by `--path <file.dd.json>` (mirrors `flow --path`). Section addressing uses stable-by-convention ids; element addressing uses the generated unique element id.

| # | Verb | | What it does |
|---|---|---|---|
| 1 | `dd create <doc-type>` | P | Instantiate a new `.dd.json` from the doc-type's registered schema + template; stamps identity, `created_at`, embedded schema ref, renders the sibling `.dd.md` |
| 2 | `dd validate` | B | Validate ONE document: schema + structural rules + id/link well-formedness. Actionable errors, one per violation |
| 3 | `dd render` | P | Re-render the deterministic `.dd.md`. `--check` is a read-only drift gate (exact `flow render --check` precedent, `E310 FLOW_RENDER_DRIFT`) |
| 4 | `dd doctor` | B | Whole-repo sweep: discover every `*.dd.json`, validate each, resolve cross-document links, detect render drift. Composed into `harness checks` by default |
| 5 | `dd set` | P | Set a scalar field or free-text section body (the overwritable-value mutation — `flow set-node --note` analogue) |
| 6 | `dd check <element-id>` | P | Tick/untick one item of a completable section, recording the required `--evidence` |
| 7 | `dd add-row` | P | Append an element; **the CLI mints the element id** and returns it in `data` (agents never invent ids) |
| 8 | `dd link` | P | Set a link-typed column/field to `{file, section, element}` — validates target doc-type, section, row, cardinality |
| 9 | `dd apply` | P | Transactional batch from file/stdin: one validation pass, one atomic write or none (direct `flow apply` precedent) |

Design notes carried from `flow`: `flow status` has no `--evidence` flag (evidence rides a separate `flow comment` call) — DD deliberately *diverges*: `--evidence` is **required** on `dd check`; a ticked item with no evidence is a validate error, not a warning. `dd add-row`/`dd link` return the minted/resolved id so an agent can chain calls without re-reading the file. A global `--quiet` slims mutation envelopes to `{path}` (flow.ts:1294 precedent).

## Part 2 — The lifecycle loop

```
① author intent → ② CLI mutation → ③ .dd.json written → ④ .dd.md regenerated → ⑤ validate/doctor → ⑥ checks gates CI
```

| Stage | What happens | Precedent |
|---|---|---|
| ③ JSON updated | Deep-clone → mutate → re-validate against the in-file schema → **atomic write** (temp + rename). Stamps `updated_at`, recomputes `content_sha256` over the **non-front-matter sections only**, so the hash does not chase its own timestamp | `runMutation` flow.ts:1267–1296 (`E302 FLOW_WRITE_FAILED`, `E303 FLOW_PATH_ESCAPE`) |
| ④ .dd.md regenerated | Automatic sibling render, `path.replace(/\.json$/,'') + '.md'`. A render failure is a stderr warning that never unwinds the committed JSON write | `autoRenderSibling`, flow.ts:113 |
| ⑥ checks gate | `dd doctor` composed as a gate inside `harness checks` — the same command CI's build-test job runs, so local and CI cannot drift | `.harness/extensions/checks/extension.ts` |

Single-writer doctrine for the RENDER (mirror of the-flow rule; first line of every rendered file, in the style of `flow-renderer.ts:367`): `<!-- GENERATED by harness dd render — do not hand-edit; regenerate from the .dd.json. -->`. Existing doctrine mirrored verbatim from `skills/builder/references/00-routing.md:234` and `docs/how/harness-flow.md:414` ("the render is a derived artifact: treat the .md like generated code"). The DD form: (1) [superseded by D1: the CLI is the *paved* writer; hand edits are legal and validation is the contract] (2) `.dd.md` is derived — never hand-edited, never parsed back into state; (3) the JSON is the single source of truth for every id, tick, evidence string, and link.

## Part 3 — `dd validate` vs `dd doctor`

| Axis | `dd validate` | `dd doctor` |
|---|---|---|
| Scope | ONE document | Whole repo |
| Checks | JSON Schema (in-file), primitive structural rules, element-id presence/uniqueness, evidence-required-when-checked, link **syntax** | All of validate, plus: cross-document link **resolution**, orphan/dangling targets, `.dd.md` render drift, content-SHA staleness, section-id convention drift |
| Can resolve links? | No — syntax only | Yes — that is the point of the sweep |
| Typical caller | An agent mid-edit, tight loop | `harness checks`, CI, `harness boot` |
| Verdict / exit | `ok`/`error` per doc · 0/1 | aggregate `error`→1 · only-soft→`degraded`→0 |

Why doctor sits in `checks` by default: `harness checks` is the one gate agents run before calling work done and the same command CI runs. A broken cross-document link fails the build exactly the way a failing test does — with the warn-launch on-ramp (`severity:'warn'` → degraded, visible, non-blocking) before promotion to a hard gate.

## Part 4 — `harness plan` as the exemplar DD consumer

Real section shapes from a live plan (063): Summary/Goals/Non-Goals (prose/list, free text) · Acceptance Criteria (`plan-acceptance-criteria`, completable-table with id, title, phase, complete, evidence, backpressure link) · Phase Index (table) · Phase N (`plan-phase-2`, completable) · **Acceptance Coverage Map (`plan-coverage-map`) — derived: computed from ACs × phases on every mutation, never authored** · Risks (mixed) · Gate Matrix (table).

What `plan` does that generic `dd` cannot:

| Capability | Generic `dd` | `harness plan` |
|---|---|---|
| Schema | reads whatever the file embeds | **knows** the plan doc-type: required sections, order, singletons |
| Section ids | accepts any `--section` string | **derives** them — `plan add-phase` mints `plan-phase-3`; you never type an id |
| Derived sections | cannot know a section is computed | regenerates the coverage map on every mutation |
| Cross-artifact wiring | sets an opaque link | SDD wiring: knows siblings (`the-flow.json`, `backpressure.dd.json`) and that ticking an AC must reflect into the flow node whose dd_link names that section |
| Back-pressure | untyped link | enforces the target is a backpressure evidence row |

Example flow: `plan create` → `plan add-phase` (returns `plan-phase-1`) → `plan add-ac` (returns `ac-01-h7f2`) → `plan link-evidence --to backpressure.dd.json#bp-evidence/row-1f07` → `plan check-ac --evidence "npm test … 12 passed at 3c3e4654"` (JSON updated, .md re-rendered, flow node recomputes its AC rollup). Under the hood every one is a `dd` mutation — **`plan` adds knowledge, not a second writer**.

## Part 5 — Architecture: composable, injected, extractable

```
L4  harness verbs      dd · plan · flow integration (commander, envelopes, exit codes, telemetry)
L3  doc-type packages  plan · backpressure · (adr, retro, …) — schema + conventions + id rules + templates
L2  dd-core            schema validation · id minting & stable-id convention · content SHA · link resolution · deterministic renderer
L1  ports (injected)   FsPort · Clock · HashPort — no node:* imports
```

Rules that keep L2 extractable (brief line 63): (1) dd-core imports nothing from harness — no envelope type, no ErrorCodes, no commander; returns plain result objects that L4 maps onto VerbResult. (2) All I/O injected — `{fs, clock, hash}`, the ports-and-adapters discipline the CLI already enforces; the existing arch test `no-direct-node-io.test.ts` fails any `node:*` import in a service, so this is enforced, not aspirational. (3) Doc types are registered, not hard-coded — a `DocTypeRegistry` keyed by string name, populated at the composition root, mirroring `buildExtensionRegistry` (no closed union, Constitution P10); an extension can register a doc type the way it registers a sensor. (4) The renderer is a pure function `(doc, docType) → string` — deterministic, no clock, no fs; a golden-fixture drift guard works exactly like `npm run check:flows`. (5) Composition root stays `app.ts`.

### Contract conventions the new verbs must follow

Canonical envelope (`command, status, timestamp, data, error{code,message,details}, evidence[], next_action`); status vocabulary exactly `ok · degraded · unconfigured · error`; exit map ok/degraded→0, error→1, unconfigured→2 (single chokepoint — only the kernel calls `process.exit`); `next_action` required whenever status ≠ ok (blank rejected by the kernel); typed errors in a contiguous block — **proposed for dd: `E320–E33x`** — referenced as `ErrorCodes.DD_*`, locked by `test/output/error-codes.test.ts`; `--json` = one `JSON.stringify` line to stdout, human diagnostics to stderr; **degraded ≠ failed, never fake green**; atomic writes (temp + rename, `E303` path-escape precedent); `dd render --check` read-only and non-zero on drift so `check:dds` can join the checks gate; extension folders need a sibling `instructions.md` or doctor wails (`E144`); durable proof declared in `evidence[]`.

### One factual detail worth locking early

The content SHA must be computed over the **non-front-matter sections only** (brief line 59), so `updated_at` changing does not change the hash — otherwise the hash chases its own timestamp and every link basis invalidates on every save. The repo already has the pattern in the wild: `docs/plans/*/backpressure-coverage.md` carries `**Basis (plan SHA-256)**: d8a6dcde…` as the exact linkage anchor a DD link should formalise.
